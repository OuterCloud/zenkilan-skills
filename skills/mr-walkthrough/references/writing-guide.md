# 走读写作指南

目标不是「解释这个 diff」，而是让读者在 8 分钟里获得一次**因果完整的开发体验**：为什么会有人改这里、他先动了哪、这一动如何传导到下游、最后人怎么验证。

## 一条主线

好的走读都有一条能被复述的主线。多数 MR 可以套这个骨架：

```
症状（谁在什么场景下坏了）
  → 根因（哪个机制在什么条件下失效）
    → 修复（先改哪、再改哪，为什么是这个顺序）
      → 下游（谁开始认它，谁仍然不认）
        → 数据（存量怎么办）
          → 验收（人怎么点一遍）
```

在 `overview.problem` 里把「症状 → 根因」讲清楚，后面的步骤才有落点。

## 每章怎么写

### 概览

- `one_liner` 用「因为 A，B 在 C 场景下坏了；这次通过 D 修复」的句式，不要写「优化了 xx 功能」。
- `problem.body` 必须出现**具体机制**：哪个函数、哪个条件、哪条链路。读者读完这段应该能自己解释故障。
- `evidence` 用可核对的现场：工作流 id、应用 id、报错原文、工单号。不要写「多个用户反馈」。
- `risk` 写这次改动**没有解决**的部分，例如存量数据、其他变体、回滚限制。

反例：

> 修复了领券重复发放的问题，提升了稳定性。

正例：

> `GrantCoupon` 走的是「先查有没有、再插入」；两步之间没有任何唯一约束兜底，并发请求和客户端重试都会查到「没领过」，然后各插一行。结果同一用户在一次活动里拿到多张券，接口两次都返回成功。

### 功能影响面

用「用户/系统能感知的行为」描述，不要用文件名代替功能。

- `fixed`：坏了，这次修好。
- `changed`：以前是 A 行为，现在是 B。
- `unchanged`：容易被误认为变了，其实没变——这一项最能体现你读懂了边界。

### 文件地图

`summary` 回答「这个文件为什么在这个 MR 里」，不是「这个文件写了什么」。

- 改动文件：说明它在链路中的角色 + 这次动了哪一块。
- 只读上下文（`context`）：说明「不看它就看不懂哪一步」。一般 2–5 个足够，不要把所有相关文件都塞进来。

### 开发链路

一条链路至少覆盖四段：入口（UI/API）→ 业务处理 → 存储 → 运行时/外部系统。

- 节点 `detail` 写「这一跳做了什么、失败会怎样」，不要写「调用 xx 服务」。
- 关键节点挂 `step`，让读者能跳进代码。
- 边标签写真实动作：`POST /api/...`、`InsertGrant`、`uk_user_activity_request`，不要写「调用」。

### 设计取舍

每个 decision 必须能独立成立：

- `question`：一个真实的岔路口，不是「为什么要改」。
- `choice`：选了什么。
- `why`：否掉了什么替代方案，为什么。
- `cost`：这个选择的代价，最好能在代码里看到（例如「新增任务类型要记得登记」）。

如果 MR 里没有明显取舍，宁可少写，也不要把实现复述成「决策」。

### 逐步走读

**切分**：一步 = 一个因果单元。判断标准是「这一步结束后，读者能回答一个完整的问题」。

**顺序**：按依赖，不按 diff 顺序。常见顺序：

1. 契约（测试/接口）——先定义「什么叫对」；
2. 机制（核心函数）；
3. 约束（为什么不能换个写法）；
4. 取舍（复用/复制、加字段/加表）；
5. 下游（谁受影响）；
6. 边界（变体、存量、回滚）。

**每步的字段**：

- `goal`：一句话，回答「这一步要解决什么」。
- `why_first`：回答「为什么现在看这里，而不是别处」。这是区分「走读」和「代码注释」的关键。
- `explain`：3–5 条，每条一个判断。不要逐行翻译代码。
- `takeaway`：读者合上页面能记住的一句话。
- `next`：把读者送到下一个问题（「那如果槽位不存在，值去哪了？」），而不是「下一节」。

**代码片段**：

- 8–40 行；超过就截取关键段，并在 `label` 里说明截的是哪一段。
- 必须从 MR head 版本复制，`highlight` 标出真正要看的两三行，不要整段高亮。
- 片段下面用 `note` 补一句「这段里容易看漏的是什么」。

### 数据库改造

没有 DDL 不等于没有数据面影响。至少要回答：

- 落库的行/字段有没有变化？
- 存量数据需不需要回填？怎么回填？
- 新旧版本能不能共存？
- 回滚时已写入的数据怎么办？

### 测试设计

- `strategy` 一句话说清「靠什么保证」：单测锁行为、集成锁链路、人工锁环境。
- `cases` 区分新增与既有；`assert` 写断言的实际内容。
- `gaps` 必须写。没有缺口的测试设计通常意味着没认真看。

### 人工验收

每一步都要能被一个不了解代码的人执行：

- `action`：去哪、点什么、填什么值。
- `expect`：页面上能看到什么。
- `observe`：去哪个区域/记录/日志确认。
- `fail`：失败时先查什么。

反例：「验证领券功能正常」。正例：「打开活动 9001 的领券页 → 用同一账号连点两次 → `coupon_grant` 只应多一行，两次都返回同一张券」。

## 语言

- 中文为主，代码、路径、参数名、报错原文保持原样。
- 动词具体：补位、落库、覆盖、拦截、展开；避免「优化」「完善」「处理」。
- 一句话只放一个判断。长句拆开。
- 不写「本次」「我们」，直接说事。

## 常见陷阱

| 陷阱 | 后果 | 改法 |
|---|---|---|
| 按 diff 顺序平铺 | 读者看完不知道因果 | 先画链路，再决定步骤顺序 |
| 把注释当行为 | 注释可能过期，走读会误导 | 以代码为准，注释只用于解释意图 |
| 把 MR 描述当事实 | 描述可能不完整 | 逐条对照代码，矛盾处写进 `open_questions` |
| 代码片段凭记忆重写 | 行号、变量名对不上 | 一律 `git show <sha>:<path>` 复制 |
| 风险写成套话 | 「注意兼容性」没有信息量 | 写具体场景与触发条件 |
| 验收写成「功能正常」 | 无法执行 | 操作 + 预期 + 观察点 + 失败排查 |
| 步骤太少 | 2 个文件的 MR 只写 2 步 | 按理解单元切，5–9 步 |
| 步骤太多 | 把每个 hunk 都开一步 | 合并同一因果单元 |

## 交付前自问

1. 一个没参与这个 MR 的同事，读完能不能复述「为什么改、改了哪、影响谁」？
2. 每个「因为/所以」都能在代码里找到依据吗？
3. 如果明天有人要回滚，页面里有足够信息吗？
4. 验收步骤里，有没有哪一步是「看情况」而不是「看到 X」？
